# Платформы и механизм запуска

Рекомендуемый Android preview — 0.4.2 ARM64. Экспериментальная 0.5.0-alpha.1 возвращает modern target36 и настольный backend с общим интерфейсом и Python/notebook-паками. [Реализованный этап и границы проверок](PYTHON-NOTEBOOKS-PREVIEW.md). Стабильного настольного выпуска пока нет.

## Современный Android

Backend совместимой сборки (`compat`) запускает инструменты из приватного каталога и по-прежнему требует `targetSdk 28`; её предупреждение о старом SDK не устранено. Экспериментальная `modern` использует target36 и нативные инструменты, установленные PackageManager: путь `execve` из writable-каталога заменён установленным хостом и `dlopen` пользовательской shared program. Проверяются оба варианта; простое изменение target не является решением.

Android запрещает прямой `execve()` файлов из домашнего каталога приложения при target SDK 29 и выше. Поэтому замена числа в Gradle или несколько одинаковых APK с разными target SDK нарушат работу локального компилятора. См. [официальное описание ограничения](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission). Для загрузки обновлений в Google Play с 31 августа 2026 нужен target API 36; нынешний APK не заявляется готовым к публикации в Play. [Требование Google Play](https://developer.android.com/google/play/requirements/target-sdk).

Для перехода нужен другой backend выполнения: установленный доверенный нативный хост для инструментов и поддерживаемый механизм исполнения скомпилированных программ либо подключение к внешнему хосту. Проверить придётся не только компиляцию, но и дочерние процессы GCC, CMake/Ninja, интерактивный ввод, GDB/PTY и доступ к файлам. До такой проверки версия с повышенным target SDK не поставляется как рабочая IDE. Настройки проверки установщика и системной защиты не отключаются.

В 0.3.0 уже ограничен открытый HTTP только loopback-адресом интерфейса, включён Safe Browsing, запрещены file/content URL и сторонние cookies WebView. Дополнительные инструменты проверяются по зафиксированным SHA256. Эти меры не подменяют переход на современный target SDK.

## Настольные версии: текущая alpha и дальнейшая работа

В 0.5 alpha общий интерфейс уже подключён к Electron/Monaco и Node-backend. На Windows реально проверены файловая система, Python, CMake/GCC/GDB/clangd и действия текущего интерфейса; собраны portable ZIP и NSIS-установщик. Переносимые файловые, Python и ручные argv-процессы проверены CI на Windows, Linux и macOS. GUI, полные нативные C/C++-сценарии и установка/удаление пакетов на Linux/macOS этим не проверены. [Точные результаты](verification-0.5-alpha.json).

Таблица ниже сохраняет направления дальнейшего отделения общих частей и проверки платформ.

| Часть | Что можно использовать | Что ещё нужно |
|---|---|---|
| Модели проекта, CMake, LSP, GDB/MI, интерфейс | Текущие JS-модули и протокол `native(op, data)` | Версионирование capabilities и независимый транспорт хоста |
| Отступы, шаблоны и кодировки | `SmartTyping`, `FileTemplates`, `FileCodec` без Android API | Отдельный общий модуль и проверки на всех ОС |
| Видимый редактор | Monaco уже хранит модели и показывает сравнения | Настольный адаптер ввода вместо Android/Sora |
| Процессы и файловая система | Операции с аргументами, проектами и потоками выделены в backend | Пути Windows, сигналы, PTY, отмена процессов и безопасное сохранение для каждого хоста |
| Компиляторы и отладчик | Модель опциональных компонентов | Собственные наборы бинарников/лицензий для каждого OS/ABI и обнаружение уже установленных инструментов |

Приоритет портирования: общий протокол и тесты, затем Linux, Windows, после этого macOS. Это направление разработки, а не уже реализованные сборки. Отдельно потребуются проверки раскладок клавиатуры, файловых диалогов, переименований с открытыми вкладками, завершения процессов и отображения пользовательских типов на каждом отладчике.
