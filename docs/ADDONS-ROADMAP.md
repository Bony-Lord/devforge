# План: модульная C++ Studio и официальный маркетплейс

Статус: **в 0.4.0 реализован [SDK preview 2](ADDON-SDK.md)**: локальные пакеты данных, профиль, транзакции/откат, обновления версий, зависимости и составные паки; модули функций хоста, синтаксиса/представлений и адаптеры native-инструментов. Ниже описана полная целевая архитектура. Удалённый маркетплейс, изолированный сторонний код, вынос всех исполняемых частей из APK, Python/ipynb и универсальные run/debug-провайдеры остаются дальнейшими этапами.

## Целевой результат

Начальный APK становится небольшим Android-хостом: запуск приложения, установка компонентов, ввод, хранение, связь с системой и восстановление. GCC и CMake из него убираются. При первом входе приложение автоматически устанавливает обязательные аддоны и предлагает выбрать опциональные, с быстрой настройкой, полной установкой, выборочной установкой и возможностью пропустить необязательное. До завершения установки виден понятный ход подготовки; неготовые команды не имитируют работающий компилятор.

**CMake — обязательная зависимость выбранного CMake/C++-пака, отдельный аддон. Компиляторы GCC, Clang и их версии — выборочные аддоны.** Уточнение для многоязычной архитектуры: пустой проект и Python-пак не должны принудительно устанавливать CMake. Интерфейс должен позволять работать с текстом и просматривать проекты, даже если компилятор не выбран.

Через официальный встроенный маркетплейс пользователь устанавливает, обновляет, отключает, удаляет и настраивает аддоны. Максимальная кастомизация переносится в них; аддоны могут иметь собственные настройки, команды, кнопки, панели, вкладки, горячие клавиши и локализации.

## Первые официальные аддоны

| Компонент | Назначение | Первоначальный выбор |
|---|---|---|
| Редактирование C/C++ | Документы, подсветка, история, навигация | Обязательный редактор |
| CMake | CMake-проекты и конфигурация сборки | Обязательный |
| GCC + sysroot | Компилятор и совместимые стандартные библиотеки | На выбор, несколько версий |
| Clang + sysroot | Альтернативный компилятор | На выбор, несколько версий |
| clangd | Диагностика, семантика, дополнения | Рекомендуемый, опциональный |
| clang-format | Форматирование, пресеты и настройка | Рекомендуемый, опциональный |
| GDB / отладчик | Протокол, переменные, точки останова | Опциональный |
| Git | История, изменения, ветки и удалённые репозитории | Опциональный |
| Оконный интерфейс | Плавающие окна, группы вкладок, привязка | Опциональный; базовый фиксированный интерфейс остаётся доступен |
| Клавиатуры | PC/Android-раскладки, комбинации и модификаторы | По выбору |
| Темы и наборы значков | Оформление и цветовые схемы | По выбору |
| Профили и шаблоны | Наборы расширений, создание проектов и файлов | По выбору |
| Официальный Python pack | Интерпретатор, venv, пакеты, анализ, форматирование и отладка Python | Ближайший языковой этап после SDK |
| Официальный Notebook pack | Документы `.ipynb`, ячейки, выводы, ядра выполнения | Ближайший этап вместе с Python |

Модули поддержки C/C++ и сервисы CMake/отладки должны иметь переносимое ядро; Android, Windows, Linux и macOS предоставляют отдельные адаптеры хоста и подходящие сборки инструментов. Это план кроссплатформенной архитектуры, а не заявление о готовности настольных версий.

## Многоязычная основа и ближайшие Python / ipynb

Уточнение от 2026-10-27: хост не должен зависеть от C/C++ как единственного языка. Официальные языковые паки объединяют независимые провайдеры: определение языка и типов документов, редактор/подсветку, диагностику/LSP, форматтер, шаблоны проектов, окружения инструментов, типы конфигураций запуска и адаптер отладки. Общие сервисы хоста отвечают за версии документов, отмену задач, файловую систему, процессы, диагностику, команды и состояние панелей. Настройки и UI-формы провайдеров описываются версиями схем; существующие C/C++ конфигурации потребуют миграции на этот контракт. Текущий JSON редактор конфигураций не является готовым SDK.

Python pack должен включать выбор и проверку версии Python, проектные окружения/venv, управление зависимостями, запуск файлов и модулей, статический анализ и отладчик через адаптер. На Android и настольных ОС нужны разные проверенные runtime-артефакты, без обязательной установки Python для пользователей только C/C++.

Notebook pack хранит `.ipynb` как структурированный документ: устойчивые ID и порядок ячеек, Markdown/код, metadata, execution count, типизированные MIME-выводы, изображения и ошибки. Нужны сохранение неизвестных полей без потерь, восстановление несохранённых изменений, undo/redo ячеек, отдельные команды запуска/прерывания/перезапуска ядра и протокол связи с выбранным kernel. Просмотр ноутбука работает без ядра; выполнение требует выбранного runtime. HTML/JS-выводы из чужого ноутбука не получают полномочия хоста. Просто открыть JSON или отправлять все ячейки в один терминал не считается поддержкой notebooks.

Визуальные аддоны отдельно объявляют темы, значки, раскладки, виджеты и оконный менеджер. Пакет языка может рекомендовать их, но не должен жёстко привязывать документы и запуск к конкретной теме или оконнику. До реализации менеджера зависимостей, изоляции и жизненного цикла это остаётся архитектурным планом, не включённым в APK 0.3.5.

## Контракт аддона

Манифест описывает стабильный идентификатор, автора, версию, лицензию, локализации, поддерживаемые ОС/ABI, минимальную версию API хоста, зависимости, конфликты и точки расширения. Один компонент может поставлять несколько версий инструментов, не подменяя версию самого приложения.

Публичный SDK предоставляет:

- сервисы документов, файлов, проектов, сборки, анализа и отладки;
- регистрацию команд, сочетаний, пунктов меню, действий, панелей и вкладок;
- схемы настроек, миграции и экспорт/импорт профиля;
- объявления зависимостей и предоставляемых возможностей;
- события жизненного цикла с отменой задач, корректным завершением и освобождением ресурсов;
- отложенную загрузку по открытию проекта, языка или инструмента.

Обновление API версионируется. Несовместимое расширение отключается с объяснением и возможностью возврата. Базовые действия открытия, сохранения и восстановления проекта не зависят от работоспособности оконного или тематического аддона.

### Типы проектов, ручной контроль и расширения как моды

Тип проекта объявляет возможности и рекомендуемые шаблоны; общий движок не считает каждый проект CMake-проектом. Смешанный проект объединяет несколько провайдеров (например, C++-библиотека, Python-скрипт и notebook) и может иметь разные конфигурации с независимыми runtime/окружениями. Специализированный редактор формы предоставляется соответствующим паком; общий редактор показывает исходную схему/JSON, неизвестные расширенные поля сохраняются без потерь.

«Пустой / вручную» — полноценный тип: без генерации обязательных исходников и CMakeLists, с командами сборки/запуска, рабочей папкой, окружением, зависимостями задач и возможностью редактировать сырые параметры. Шаблон не должен скрывать доступ к низкоуровневым настройкам. Конфигурации сохраняют тип провайдера, его версию схемы и миграции, а не глобальный фиксированный список языков. В 0.3.5 ручные argv-команды и JSON относятся к текущему встроенному редактору; будущие произвольные провайдеры ещё не реализованы.

Запрошенная глубина — моды приложения: регистрация новых окон и типов окон, собственные редакторы документов, вкладки, замена существующих компонентов, переопределение или оборачивание обработчиков, правила ввода и навигации, запуск/сборка, темы и компоновка. SDK должен поддержать идентифицированные точки замены и middleware с порядком приоритетов, обнаружением конфликтов и возможностью отключить конкретное переопределение. Разрешения, API жизненного цикла и режим восстановления сохраняются; мощность мода не означает неотслеживаемую порчу состояния хоста. Нужны отдельные контракты UI, фоновых расширений и нативных runtime, а также диагностика влияния аддона на зависания/ошибки.

## Официальный маркетплейс и доставка

Сначала официальный каталог поддерживается проектом; затем можно открыть публикацию сторонним авторам. В карточке видны назначение, автор, версия, совместимость, размер загрузки/установки, лицензия, изменения и зависимости. Есть кнопки установки/обновления/удаления рядом с компонентом, каналы stable/preview, поиск и фильтры.

Каталог и пакеты имеют проверяемое происхождение: подписанные метаданные, контрольные суммы и отдельные артефакты по платформам/ABI. Установка проходит через временный каталог, проверку, атомарную активацию и откат. Поддерживаются прерванная загрузка, нехватка места, отмена, кэширование, экспорт пакета и установка из локального файла. Обязательный CMake нельзя случайно удалить как зависимость работающего профиля; его можно обновить или восстановить.

Для GCC и других компонентов сохраняются точные соответствующие исходники, лицензии и уведомления для каждой распространяемой версии. Размер начального APK проверяется отдельно от размера выбранной установки.

## Граница хоста и аддонов

Стороннее расширение не получает прямой общий `ForgeNative` или неограниченный доступ ко всем проектам. Нужны изолированное выполнение UI-кода и API с явно предоставленными возможностями: выбранные файлы/проекты, процессы инструментов, сеть и системная интеграция. Нативные инструменты и UI-расширения имеют разные загрузчики и контракты. Установка произвольного аддона не должна позволять переписать хост или обойти отключение его возможностей.

Перед выносом инструментов из APK требуется завершить и проверить современный механизм исполнения Android: перенос бинарника в загружаемый архив сам по себе не решает ограничения выполнения на новых target SDK. Это зависимость архитектурного этапа; текущая поддерживающая ветка target SDK28 не считается решением для будущей публикации в Play.

## Этапы реализации

1. Зафиксировать SDK и точки расширения, отделить переносимое ядро от Android-хоста, описать зависимости и форматы профилей.
2. Перевести текущие пакеты инструментов на единый манифест, менеджер зависимостей и атомарную установку с откатом. Проверить современный Android runtime.
3. Вынести CMake, GCC/Clang, clangd/форматтер, GDB и Git в официальные пакеты. Собрать минимальный APK без GCC/CMake и проверить чистую установку.
4. Добавить первый запуск с обязательными и выборочными компонентами, официальный каталог и управление версиями.
5. Вынести оконник, клавиатуры, темы, шаблоны и прочие UI-возможности на тот же SDK; сохранить простой режим восстановления.
6. Опубликовать SDK, примеры расширений, правила совместимости и приём сторонних пакетов; затем расширить платформенные адаптеры.

## Условия готовности

На чистом устройстве минимальный APK устанавливает обязательные компоненты; выбранный GCC или Clang действительно собирает и запускает C/C++ проект. Без компилятора остаётся рабочее редактирование. Отключение оконника возвращает фиксированный интерфейс без потери документов. Обновления и ошибки зависимостей проходят с откатом. Прерванная установка, отсутствие сети, нехватка места и несовместимый пакет не повреждают проекты. Совместимость и сценарии восстановления подтверждаются автоматическими и физическими проверками, а не только наличием карточек в каталоге.
